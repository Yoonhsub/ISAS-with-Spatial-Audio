# MOBI_Finals 승객·기사 반복 시연

## 구현 흐름

1. 승객 로그인 → 실제 API 모드 → 노선 정보 → 음성으로 질문하기.
2. `충북대학교병원 가고싶은데 몇 번 버스 타?`처럼 목적지가 포함된 고정 문장으로 질문한다.
3. 서버가 정류장 이름에서 부분 일치 후보를 검색한다. 후보가 하나여도 선택을 거친다. 내부 CJB ID는 읽지 않고 실제 노선의 다음 정류장에서 확인한 `○○ 방면`으로 동명 정류장을 구분한다. `1번` 같은 선택 번호나 안내한 방면으로 확정할 수 있다. 방향 정보가 없으면 확인이 필요하다고 알리며 임의로 방향을 만들지 않는다.
4. 확정한 하차 정류장과 현재 GPS 위치로 기존 노선 탐색기를 호출한다. `타실 곳은 ○○ 정류장입니다. △△ 방면으로 가는 N번 버스를 타세요. □□ 정류장에서 내리세요.` 순서로 승차·방면·버스·하차를 구분한다. 위치 권한 또는 연결 가능한 노선이 없으면 다음 단계로 진행하지 않는다.

실제 TAGO 경로 검색은 직통이 없을 때 1회 환승도 탐색한다. 출발·목적지 주변 후보 각각 최대 5개 정류장의 경유 노선에서 각 측 최대 12개 노선의 정류장 순서를 검증한다. 두 구간 모두 운행 순서가 맞고 동일 정류장 ID에서 갈아탈 수 있어야 한다. 도로 반대편 또는 인근 다른 정류장으로 걷는 환승과 2회 이상 환승은 현재 지원하지 않는다. 일부 외부 조회가 실패하면 검증된 노선만 사용하고, 확인된 경로가 없을 때는 조회 실패를 구분해 알린다.

정류장을 선택한 뒤에는 조회된 후보 중 기존 순위 점수가 가장 높은 추천 경로 하나만 안내한다. 환승 횟수·도보 거리·경유 정류장 수·도착/방향 정보의 확인 여부 등을 반영한 순위이며 실제 최단시간을 보장하지 않는다. 고정 음성 대화에 반환하고 저장하는 경로 목록도 추천 하나로 제한하여, 안내하지 않은 대안 경로의 버스 번호로 탑승 요청이 생성되지 않게 한다. 추천 경로의 첫 승차·환승·최종 하차 안내는 모두 유지한다.

추가 실제 데이터 확인(2026-11-24): 공개 예시 출발지인 충북대학교병원 좌표에서 `시외버스터미널`, `상당공원`, `오송역` 질문의 후보 선택 → 단일 추천 → 첫 버스 음성 확정을 확인했다. 해당 조건에서 시외버스터미널은 20-2번, 상당공원은 인근 송학삼익맨션아파트.충북대학교병원 정류장의 844번, 오송역북문(만수초등학교 방면)은 823번 → 사창사거리 → 511번이었다. 이 번호들은 고정 시연 데이터가 아니며, 실제 위치와 선택 방면에 따라 다시 계산한다. 사용자 GPS 재현·실기기 음성 인식·실제 요청 생성은 이 조회 검증에 포함하지 않는다.

환승 음성은 `첫 승차 정류장·방면·버스 → 갈아탈 정류장 → 다음 버스·방면 → 최종 하차 정류장` 순서다. 먼저 첫 버스 번호로 탑승 요청을 보낸다. 첫 요청이 승인된 뒤 환승 정류장에서 다시 음성 화면을 열어 `다음 버스 번호 + 번 버스 탈게`라고 말하면, 첫 요청을 COMPLETED 이력으로 옮기고 환승 정류장·두 번째 노선의 새 WAITING 요청을 만든다. 기사는 일반 요청과 동일하게 승인·거부·취소한다. 두 번째 요청도 승인되기 전에는 장애물 탐지 권한을 얻지 못한다. 거부·취소된 두 번째 요청은 같은 번호를 다시 말해 일반 생성 API로 재요청할 수 있다.

첫 요청 생성 시 서버가 확정한 경로를 요청 기록의 내부 메타데이터에 함께 저장한다. `POST /ride-requests/{requestId}/transfer`는 클라이언트가 보낸 버스 번호를 저장된 다음 구간과 대조하고, RTDB 트랜잭션으로 첫 요청 완료와 후속 요청 생성을 함께 처리한다. 동일 부모 요청의 후속 요청 ID는 고정되어 응답 유실·중복 호출에도 중복 생성되지 않는다. 승객 앱은 처리 중인 환승 요청을 계정별로 저장해 재시도한다. 다른 사용자·미승인/취소된 첫 요청·다른 버스 번호로는 다음 구간을 만들지 않는다.

기존 기사 웹은 활성 요청을 받으면 자동 조회를 멈추므로, 환승 요청을 보낸 뒤 기사 웹에서 ‘요청 목록 새로고침’을 눌러 두 번째 요청을 확인한다. 이때 완료된 첫 요청은 이전 기록으로 이동한다.
5. 안내된 `711번 버스 탈게`처럼 말하면 서버가 안내한 노선인지 검증하고 승차 정류장과 노선을 확정한다. 승객 앱이 인증된 HTTP 요청과 재시도 식별자로 탑승 요청을 생성한다.
6. 기사 웹은 활성 요청이 없을 때 1분 간격으로 요청을 갱신한다. 수락 `ACCEPTED`, 거부 `DENIED`, 수락 후 취소 `CANCELLED`를 지원한다. 취소 플래그 철자는 기존 계약의 `CANCELLED`로 통일한다.
7. 승객 앱은 수락 후에도 5초 간격으로 상태를 조회한다. 거부·취소·완료는 활성 요청에서 제거하고 이전 기록에 남긴다. 새 요청을 보낼 수 있고 앱 재실행 시 서버에서 본인의 요청을 복원한다.
8. 장애물 탐지 화면의 카메라는 본인의 승인된 요청을 확인한 뒤 실행한다. 실행 중 승인 취소/상태 조회 실패 시 안내를 중지한다. 카메라 동작 중에는 3초 간격으로 승인을 재확인한다.
9. 객체명 인식 문장을 TTS로 안내한 뒤 현재 카메라의 해당 객체 위치와 스마트폰 회전 센서를 기존 Android 양이 공간음향 엔진에 전달한다. 이 모드는 BLE 비콘을 요구하지 않는다. 카메라 객체 인식은 차량 번호 식별을 의미하지 않는다.

객체 음성 안내는 위치 변화와 구분한다. 동일한 종류의 안내 대상은 좌우 이동이나 일시적인 검출 누락 후 중앙 재검출 때 객체명을 반복하지 않고 비프음으로 위치를 갱신한다. 중앙은 0도 양이 비프음을 사용한다. 다른 종류가 안내 대상으로 선택되거나 탐지를 다시 시작하면 객체명을 다시 안내한다. 이는 종류 기준 중복 억제이며 개별 객체의 동일성을 추적하는 기능은 아니다. 새 검출 없이 방향을 유지하는 시간 제한(회전 센서 사용 시 최대 4초, 카메라만 사용 시 1초)은 유지한다.

## 공통 서버와 계정

- 두 앱 모두 `MOBI_API_BASE_URL`로 동일한 FastAPI 서버를 사용한다. 앱이 RTDB에 직접 탑승 요청을 쓰지 않는다.
- 요청/이력은 Firebase RTDB에 보관한다. `GET /ride-requests`는 인증된 승객 본인의 기록만 반환한다.
- `/drivers/{driverId}`의 `active: true`, `acceptsSelectedRoutes: true`는 승객이 확정한 노선의 요청을 받는 기사 계정을 지정한다. 승객의 `routeId`, `busNo`, `stopId`는 그대로 보존한다. 고정 노선 기사(`routeId`, `busNo`)가 있으면 그 기사를 우선하며, 대상 기사가 없거나 여러 명이면 409를 반환한다.
- Firebase 로그인 계정에 `mobi_role=passenger` 또는 `mobi_role=driver`가 필요하다. 기사는 `mobi_driver_id`도 해당 기사 ID와 일치해야 한다.
- 정상 서버는 `FIREBASE_USE_MOCK=false`, `FIREBASE_USE_ADC=true`, `PUBLIC_DATA_USE_MOCK=false`, `MOBI_PASSENGER_CAMERA_PREVIEW=1`을 사용한다. 시험 전용 `MOBI_CLOUD_TEST*` 설정은 별도로 검토한다.
- 안내 대화/카메라 세션은 기존 메모리 저장소를 사용하므로 단일 프로세스, Cloud Run 최대 인스턴스 1이 필요하다. 서버 재시작 시 진행 중 대화는 다시 시작한다. 탑승 요청 이력은 RTDB에 유지된다.

## 재현 빌드

검증 SDK: Flutter **3.41.9**, Dart **3.11.5**. Android는 플러그인별로 SDK Platform 34/35/36, Build Tools 34.0.0/35.0.0/36.0.0, NDK 28.2.13676358, CMake 3.22.1을 사용한다. 저장소의 Gradle 8.14, AGP 8.11.1을 유지한다.

Firebase 공개 앱 설정은 소스 저장소 밖의 JSON 파일에 넣는다. Android는 `google-services.json`에 등록된 Android 앱 ID를, 웹은 웹 앱 ID를 사용한다. 필요한 키는 기존 `infrastructure/firebase/web-defines.example.json`의 다섯 키와 `MOBI_API_BASE_URL`이다.

Android 카메라 컴파일의 `CallbackToFutureAdapter` 누락을 해결하기 위해 CameraX 플러그인의 `implementation`에 `androidx.concurrent:concurrent-futures:1.2.0`을 명시했다. 기존 Flutter 버전을 유지하면서 공식 수정과 같은 의존성 보완을 적용했다: https://pub.dev/packages/camera_android_camerax/changelog

```powershell
./scripts/build_demo.ps1 -App driver -DefinesFile C:/configs/driver-web.json -Output C:/builds/driver-web
./scripts/build_demo.ps1 -App passenger -DefinesFile C:/configs/passenger-android.json -Output C:/builds/passenger
```

두 명령은 일반 `lib/main.dart` 진입점으로 독립 실행 결과물을 만든다. 승객 앱 표시 이름과 APK 파일명은 `MOBI_Finals_승객`, `MOBI_Finals_승객.apk`이며 기사 웹 제목은 `MOBI_Finals 기사`다. Firebase 등록과 연결된 Android 패키지 ID는 유지한다. APK는 현재 저장소의 개발용 서명 설정을 사용하므로 시연 설치용이다. 기사 웹은 정적 호스팅에 배포하고 그 HTTPS Origin을 백엔드 CORS 및 Firebase 승인 도메인에 등록한다.

## 검증 한계

음성 화면은 실제 인식기 상태에 맞춰 `듣는 중`, `마이크 연결 중`, `음성 확인 중`, `답변 준비 중`, `답변 읽는 중`, `음성 입력 대기`를 크게 표시한다. 시작 실패 때는 `마이크 확인 필요`로 안내한다. 답변이 끝난 후 다음 발화는 마이크 버튼을 한 번 눌러 시작한다. Android 인식 종료·오류 콜백에서는 자동 재시작하지 않는다. 무음으로 입력이 끝나면 대기로 돌아가고 사용자가 다시 마이크를 누른다. 취소와 새 인식 시작을 직렬화하고 연속 탭은 한 번으로 처리한다. 화면을 다시 열면 공유 음성 인식기의 상태·오류 콜백을 새 화면으로 갱신한다.

버스 번호는 화면과 요청 데이터에 원래 표기(예: 711-1)를 유지하고 음성에서만 “711 다시 1번 버스”로 읽는다. “711 다시 1번 버스 탈게”라는 입력도 711-1 노선으로 정규화한다. 승차 안내 마지막의 버스 선택 요청은 서버가 제공하는 문장 한 번만 전달한다.

단위/위젯 테스트는 실제 음성 인식, 실도로 버스 도착, 실기기의 회전 센서·이어폰 청취를 대신하지 않는다. 배포 후 별도 승객·기사 계정으로 승인 → 취소 → 재요청, 거부 → 재요청, 앱 재실행 및 실제 Android 카메라/이어폰 시연을 확인해야 한다.

기사 웹 자동 갱신: 진행 중인 요청이 없을 때만 1분마다 조회한다. WAITING/NOTIFIED 요청을 수신하면 멈추고 ACCEPTED 상태에서도 멈춤을 유지한다. 승인·거부·취소 직후에는 목록을 한 번 갱신하며, 마지막 활성 요청이 종료된 것을 확인하면 1분 조회를 재개한다. 중지 중의 승객 취소나 추가 요청은 ‘요청 목록 새로고침’으로 확인한다. 조회 오류만으로 자동 갱신을 재개하지 않는다.

승인 후 카메라 실행: 승객 홈의 ‘장애물 탐지’를 한 번 누르면 본인 요청의 ACCEPTED 상태를 확인하고 카메라 화면을 연다. 포함된 모델 준비 후 카메라·객체 탐지·음성 안내를 자동으로 시작한다. 초기 ‘카메라 시작’ 버튼 단계는 없다. 최초 카메라 권한 요청은 Android에서 허용해야 한다. 준비 중 승인 취소·계정 변경·화면 종료·백그라운드 전환 시 시작하지 않으며, 오류/중지 후에는 ‘다시 시도’ 또는 ‘탐지 다시 시작’으로 명시적으로 재시도한다.


## 승객 화면과 승인 음성 알림

실서비스 노선 검색에서는 ‘채팅으로 질문하기’ 진입점을 제거하고 음성 질문만 제공한다. 공통 대화 세션, API 호출, 선택 경로, 탑승 요청과 음성 종료 로그 처리는 유지한다. 보행 지도와 보행 상세 안내는 제거하고 버스·환승·도착 정보만 표시한다. GPS 보행 음성 안내는 제공하지 않으므로 TMAP 키는 필요하지 않다. 출발 정류장/버스 추천에 필요한 위치 조회는 유지한다.

음성 화면의 사용자/모비 자막은 기본 크기 22, 처리 중 자막은 20이다. 마이크 상태 표시와 버튼 크기는 유지한다.

탑승 요청을 전송한 뒤 음성 화면을 닫고 승객 홈의 상태를 확인한다. 본인의 현재 요청이 ACCEPTED임을 확인하면 ‘탑승 요청이 수락되었습니다.’라고 안내한다. 계정과 요청별 성공 발화를 로컬에 저장해 반복 조회·재진입 시 중복하지 않는다. 새 환승 요청은 별도로 안내한다. 화면 비활성·백그라운드·계정 전환 때는 발화를 중지하며 이후 유효한 조회에서 재시도한다. 푸시/백그라운드 알림을 추가하는 기능은 아니다. 기존 안전 안내의 발화 우선순위를 유지한다.
